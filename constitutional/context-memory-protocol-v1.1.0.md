## Purpose

Agents run inside finite context windows and cost real tokens. Left
unmanaged, this framework's own strengths — rich definitions, full
audit logs, constitutional documents — become its performance problem:
a single agent naively loading its full definition, the full ECL, the
AOM, and the raw engagement log would spend most of its context before
doing any work, and the spend recurs on every run. This protocol makes
context loading deliberate and gives the framework a real long-term
memory.

---

## Rule 1 — Layered Context (cards, not tomes)

Every document an agent consumes exists in two layers:

| Layer | What | When loaded |
|-------|------|-------------|
| **Card** | 1-page summary, versioned against its source | Default — loaded at agent kickoff |
| **Full document** | The complete source | On demand only, via query to the owning orchestrator |

Mandated cards:

- **ECL summary card** (`templates/ecl-summary-card-template.md`) —
  regenerated by `ecl_orchestrator_agent` on every ECL version bump.
  Roster agents receive the card in `engagement_context`; only
  orchestrators may pull full ECL sections, via the existing ECL query
  protocol.
- **AOM summary card** — the one-page operating rules every agent needs
  (naming, non-fabrication, handoff contract, escalation timeouts,
  Section 7.1 stop conditions). Full AOM is loaded only by
  `ai_manager_agent` and validators.

**Staleness rule:** every card carries the version of its source. A card
whose source version differs from the registry's current version is
stale — using it is a compliance failure (equivalent to acting on an
unacknowledged cascade).

## Rule 2 — Lean Runtime Definitions

Agent YAML files serve two consumers with different needs: the model
at runtime (goal, backstory, constraints, cycle, current task) and the
governance layer (versions, lifecycle, compliance metadata, full
playbooks).

**Rule:** the runtime loads a *runtime extract* of the agent definition —
goal, backstory, constraints, condensed cycle, the relevant handoff
contract, and quality gates. Governance metadata, full decision-logic
playbooks, and KPI frameworks are not shipped into every model call;
they are consulted at plan time or by the orchestrator.

Application is progressive: each agent adopts an explicit runtime
extract at its next MINOR bump. Until then, orchestrators SHOULD trim
governance metadata when constructing agent prompts.

## Rule 3 — Log Rotation & Distillation

Append-only logs are the audit trail (C6) — they are **never** an agent
input in raw form beyond the current cycle.

- **Monthly** (with the management review): each instance's engagement,
  override, and query logs are distilled into a rolling summary
  (`logs/summary-rolling.md`): decisions made, overrides and outcomes,
  open threads. Raw entries stay in the archive, untouched.
- Agents needing history load the **rolling summary**, never the raw log.
- `ai_manager_agent` triggers the distillation as part of its monthly
  cadence and audits that it happened.

## Rule 4 — Learnings Memory (the framework's long-term memory)

Raw LEARN-phase output is high-volume and low-density. Memory is what
survives distillation:

```
Agent LEARN phase
  → learning-log entries (templates/learning-log-entry-template.yaml)
     one structured entry per learning, evidence-linked
    → MONTHLY: roster orchestrator distils entries into the roster's
      learnings.yaml (templates/learnings-memory-template.yaml)
      - what_works / what_fails / client_specifics
      - every insight carries evidence_refs back to raw entries
      → QUARTERLY: ai_manager_agent reviews across rosters
        - insights that should change behaviour permanently become
          version-bump proposals (the definition IS the memory of record)
        - actioned learnings move to actioned_into_definitions
        - no-longer-true insights move to retired (kept for audit)
```

**Loading rule:** agents load their roster's `learnings.yaml` (plus the
business's client_specifics) at kickoff. It is a card-sized file by
design — if it outgrows ~2 pages, the orchestrator must distil harder,
not load more.

**No vector stores at this scale.** Curated, versioned, auditable YAML
memory fits the framework's governance model and its actual volume.
Adopting retrieval-scale memory (rung 4 of the Retrieval Ladder, Rule 6)
is a MAJOR bump to this protocol with human sign-off — and it is
justified only when a rung-4 escalation trigger is **measured**, not
anticipated: cross-client learnings memory exceeding card size after
honest distillation (empirically ~20+ concurrently served clients);
logged, recurring retrieval failures at rung 2/3; or semantic
cross-engagement queries becoming a routine access pattern rather than
an exception. Absent a measured trigger, the ladder stops at rung 3.

**Offboarding:** the memory harvest step in the Engagement Lifecycle
close-out is mandatory — an engagement's learnings outlive it.

## Rule 5 — Token Budgets

- Every orchestrator declares a per-agent-run context budget in its
  engagement plan (default guidance: cards + brief + task inputs;
  target ≤ 25% of the run's context window on standing material).
- Handoff briefs remain **self-contained** (AOM S3.1) — that rule is
  the single biggest token saver in the framework: receiving agents
  never need the sender's history.
- Outputs consumed by other agents are structured (YAML) and minimal;
  prose is for humans.
- `ai_manager_agent` tracks cost-per-outcome (ECL AI Manager domain
  metric) and flags engagements whose context spend grows
  cycle-on-cycle — that is drift, in token form.

## Rule 6 — The Retrieval Ladder

Memory is only useful if it can be found again. Retrieval mechanisms
sit on a **ladder** of increasing power and cost. The rule is
**escalate only on MEASURED failure** — you climb a rung when the rung
below is demonstrably, repeatedly insufficient, never on anticipation
or fashion. Cheaper rungs are more auditable; the framework prefers the
lowest rung that works.

| Rung | Mechanism | What it retrieves | Cost / auditability |
|------|-----------|-------------------|---------------------|
| **1** | **Cards** (Rule 1) | The card-sized standing set: ECL/AOM cards, roster `learnings.yaml`, `client_specifics` | Cheapest, fully versioned, loaded at kickoff |
| **2** | **Agentic file search** (grep/glob over the instance + framework repos, orchestrator-mediated) | Specific facts from raw logs, full documents, prior outputs — pulled on demand | Cheap; every hit returns a **file + line citation** |
| **3** | **Keyword / DB index** (structured index over logs, learning-log entries, engagement records) | Term/attribute lookups across volume that grep no longer serves efficiently | Moderate; rows carry source IDs |
| **4** | **Vector RAG** (semantic embedding store) | Semantic / cross-engagement similarity queries no lower rung can answer | Highest cost, lowest native auditability — **MAJOR bump, human sign-off** (Rule 4) |

**Provenance is mandatory at every rung.** No rung may return a fact
without a traceable source — a card carries its source version, a file
search returns a file+line citation, an index row carries its source
ID, and any rung-4 result must resolve back to the underlying
learning-log entry or log line it was distilled from. A retrieval that
cannot cite its source is treated as fabrication (AOM S8.4) and must not
be acted on. Rung 4 does not relax this; if anything it raises the bar,
because embeddings otherwise launder provenance.

**Rung-4 escalation triggers (all must be MEASURED, not forecast):**

- **Card-size overflow after distillation.** Cross-client learnings
  memory that still exceeds card size *after* honest distillation —
  empirically around **20+ concurrently served clients**, where the
  generalisable pattern set genuinely outgrows a curated ~2-page file.
- **Logged retrieval failures.** Rung 2/3 failing to surface known-present
  information on a recurring, *logged* basis (not one-off misses).
- **Routine semantic cross-engagement queries.** Semantic "what have we
  learned across engagements like X" queries becoming a standing access
  pattern rather than an occasional exception.

Until such a trigger is measured and recorded, the ladder stops at
**rung 3**. Rungs 1–3 are available now and require no bump; rung 4 is
the reserved, sign-off-gated escalation described in Rule 4.
